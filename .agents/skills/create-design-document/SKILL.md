# Create Design Document

## 工作流

1. 定位目录：用户指定位置优先；否则沿用项目约定；均无时使用项目根下的 `document/design/`。不得建立第二套设计目录。
2. 读取目录 `README.md` 并遵循其 scope、权责和索引；不存在时从 `assets/design-readme-template.md` 初始化。
3. 核对相关代码、契约、文档和测试，区分当前实现、确定设计与待决问题。事实冲突或关键边界不明确时先询问，不固化猜测。
4. 确定唯一权威文档：已有主题更新原文档；新主题先在 README 中登记叙事权责。
5. 创建或更新设计。开头固定为 `## 简述` 和 `## 职责`：前者说明主题与目的，后者说明本文负责与不负责的边界；之后按内容需要自由编排。
6. 同步 README 的叙事权责和设计列表。其他位置只保留必要摘要和相对链接，删除无独立职责的重复正文。
7. 验证链接、主题重复、术语、状态标注、验收口径，以及设计与代码、契约、测试是否冲突；发现冲突必须消除。

## 规则

- 只收录已确定、可执行且需跨任务复用的设计；待决内容必须明确标注。
- 同一规则只在一份权威文档中完整定义；引用不存在的文档时标注“待补充”。
- 跨文档复用优先链接到权威文档的具体标题，不重新描写整段内容。
- 文档使用可链接的标题组织内容；标题按主题边界和导航需要设置，不规定固定层级或数量，避免碎片化标题和无标题长文。
- `简述`、`职责`后的结构自由，但同一项目、同一层级文档应沿用一致的命名、层级和表达风格。
- 在流程、状态转换、组件关系、数据流或时序等适合图示的地方，可以使用 Mermaid；图示能比长段文字更清晰地表达设计时，应优先用图，并只补充必要说明，避免装饰性作图。
- 文档描述意图、边界、规则和验证口径；实现细节以代码为准，可执行接口以 schema、OpenAPI 或协议定义为准。
- 文件名简短、具体、人类可读，默认 `<主题>设计.md`；一套内聚设计对应一个文件。
- 仅在同一 scope 有多份稳定设计时建立子目录；子目录必须有自己的 `README.md`。

## README

`README.md` 类似该 scope 的 `cp-meta.md`，只管理目录，不承载具体设计。它维护：

- 目录角色、收录边界和管理规则；
- 主题到权威文档的叙事权责；
- 有效设计索引和子目录边界；
- 新增、修改、拆分、合并、替代和删除规则。

设计变更必须在同一次任务中同步 README。空目录允许索引为空。

## 不收录

- 草案、任务和进度：控制平面、任务板或 issue；
- 决策过程和备选方案：ADR；
- 实现盘点、运行和部署说明：工程文档；
- 外部原始资料：reference 目录。
