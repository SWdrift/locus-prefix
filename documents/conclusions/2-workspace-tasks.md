# 工程任务闭环与可解释失败

`commit` 引用包含本实验与结论的标签 `2-workspace-tasks`，可通过该标签复现实验。

关联[案例 A](../cases/1-heterogeneous-engineering-workspace.md)的[发现与表达](../cases/1-heterogeneous-engineering-workspace.md#31-发现与表达)、[组合已有能力](../cases/1-heterogeneous-engineering-workspace.md#4-持续演化情境)及[处理失败与副作用](../cases/1-heterogeneous-engineering-workspace.md#4-持续演化情境)。支持并限定[第一轮操作目录结论](1-core.md#实验-2操作发现组合与调用边界)，不声称建立了 Core。

## 设计选择与预期收益

现有 package.json、pnpm、普通函数与 ESM 已足够执行工作区检查。缺口不是新的执行语言，而是调用者必须自己接洽任务发现、输入约定、授权与失败报告。

本轮使用两个独立包：`@locus/tasks` 负责描述与调用结果，`@locus/workspace` 只提供领域任务定义；根 `locus.tasks.js` 显式组合它们。去掉目录后原脚本仍能执行，但需要各调用方重复实现发现、输入说明和步骤结果归因。新增任务不要求继承、实体注册或修改 CLI。

结果分为 `blocked`（未进入任务 run）、`failed`（任务执行后失败）、`succeeded`。步骤保留已完成结果，不把后续失败等同于“什么都没发生”。这不是可安全恢复的证明：没有幂等性与外部状态证据，就不能从步骤记录推导自动重试或补偿。

## 错误记录 1：Windows 上可直接 spawn pnpm —— 已否定

- **原判断**：使用 Node 的 `spawnSync('pnpm', ['--version'])` 应能复用终端里可用的 pnpm。
- **适用环境**：本工作区的 Windows、Node.js 24；终端能够执行 pnpm。
- **实际反例**：原生子进程探针返回 `status: null`、`error: ENOENT`，没有启动 pnpm。终端的命令解析不能直接等同于 `shell: false` 的进程解析。
- **影响**：不能把“终端命令存在”当作“可直接作为 spawn 的 executable”。任务接入必须处理真实执行接口，不能仅登记一个工具名称。
- **修正方向**：使用明确的 Node/pnpm 入口调用，参数以数组传递，不拼接用户 shell 输入。具体支持范围以工作区包文档和执行实验为准；不宣称已验证其他 OS。

## 错误记录 2：递归复制普通对象即足够隔离元数据 —— 已否定并修正

- **原实现**：递归复制数组与普通对象，其他值原样返回，并声称发现结果是隔离的深拷贝。
- **反例**：输入示例中放入 `new Date('2026-01-01T00:00:00Z')`，对 `show()` 结果执行 `setUTCFullYear(2000)`；再次 `show()` 实际得到 `2000-01-01T00:00:00.000Z`，目录被污染。
- **修正**：删除手写复制器，使用原生 `structuredClone`。同一个实际探针修正后返回 `2026-01-01T00:00:00.000Z`；[实验 4](../../tests/4-task-execution/demo.test.js)保留可变原生值隔离的回归断言。
- **契约代价**：输入描述必须可结构化克隆；这不等同于 JSON 可表达。CLI 的 JSON 边界仍需单独解释。这里需要隔离的是描述数据，不是克隆用户的执行函数或运行时对象图。

## 错误记录 3：pnpm exec 只是启动命令 —— 本环境下受限

- **原判断**：包正在并行创建时，先用 `pnpm exec node` 做环境探针不会影响依赖状态。
- **实际反例**：根已声明两个 `workspace:*` 依赖、但其中一个包尚无 manifest，pnpm 在执行前自动启动安装，然后报 `ERR_PNPM_WORKSPACE_PKG_NOT_FOUND`。
- **修正**：先完成各包 manifest，再统一安装与执行。不能将工作树的中间状态当作可运行交付状态。
- **影响边界**：这是本环境观察到的 pnpm 行为，不据此断言所有 pnpm 版本/配置都会自动安装。它也不是工作区包本身的功能缺陷。

## 错误记录 4：部分 YAML 解析足以报告成员 —— 已否定并删除

- **原方案**：为避免依赖，手写块列表/流式列表解析，去掉字符串外层引号后返回 packages。
- **反例**：合法 YAML `packages: ["packages/\u0061"]` 的双引号转义表示 `packages/a`；实际探针却得到字面量 `packages/\\u0061`，且结果没有标注不确定性。
- **修正**：删除部分解析器，返回配置来源与原文，明确不解释成员集合。修正后的实际探针只有 raw YAML 证据，不再给出错误的已解释路径。任务执行本身不依赖该成员列表，因此无需新增 YAML 依赖。
- **教训**：无依赖不是手写不完整解析器的理由。展示配置和解释配置是不同能力；未来确有成员查询需求时，优先使用成熟解析器或经授权调用 pnpm 查询，而不是继续修补语法分支。

## 错误记录 5：退出码 0 即执行了指定脚本 —— 已否定

- **原假设**：脚本名作为独立 argv 传给 pnpm，就能执行对应脚本。
- **反例**：在真实子进程探针中，即使 package.json 已有名为 `--help` 的脚本，`pnpm run --help` 仍退出 0，却没有执行检查；它输出的是 pnpm 帮助。
- **修正**：使用 `pnpm run -- <script>`。同一探针的 `run -- --help` 退出 0 且实际运行了检查。[实验 5](../../tests/5-workspace-integration/demo.test.js)覆盖正常名称、空格名称与 `--help`，检查真实输出及没有向脚本泄漏额外参数，不锁定启动器内部路径。
- **影响**：退出码是进程事实，不足以单独证明用户要求的动作发生了；选项解析也是工具适配契约的一部分。

## 错误记录 6：JSON 输出失败可以算作未执行 —— 已否定并修正

- **原实现**：CLI 的统一 catch 将所有异常返回为 `blocked`，包括任务完成后的 JSON.stringify 异常。
- **反例**：一个实际完成并返回 `1n` 的普通函数，CLI 返回 `blocked`、退出码 2；这错误暗示尚未执行，可能诱发有副作用任务被重复执行。
- **修正**：将输出阶段单独报告为 `status: failed, phase: report, executionStatus: succeeded`、退出码 1，不把 BigInt 强制转成含义不同的数据。同一实际 CLI 探针已观察到修正后的结果。[实验 6](../../tests/6-cli/demo.test.js)用写入完成标记的任务验证：副作用已发生，即使输出无法编码也不得谎报为未执行。
- **边界**：CLI 的结果必须可 JSON 表达；报告无法编码的结果时不能保留原值的 JSON 内容，任务是否可重试仍需独立判断。

## 实际验收

本工作区使用 `pnpm install --offline --ignore-scripts` 链接两个包，无新增外部依赖。验证路径：

| 操作 | 观察结果 |
| --- | --- |
| `pnpm test` | 56 项通过、0 失败，包含旧实验与真实 CLI 子进程 |
| `pnpm locus list` | 发现两个工作区任务及输入示例、权限、effects |
| `pnpm locus run workspace.inspect --allow filesystem:read` | 读取当前实际配置，并将 YAML 保留为原文 |
| 经显式授权执行 `workspace.check` 的 `check:baseline` | 实际执行历史实验 1–3，进程退出 0 |
| 不授权执行 `workspace.check` | blocked、退出码 2、空步骤，未进入任务 run |
| 临时 fixture 的检查脚本退出 7 | CLI 退出 1，保留 inspect 成功、execute 失败及 stdout/stderr |
| 显式修正该脚本后再次运行 CLI | 新执行成功、进程退出 0，无隐式重试或续跑 |

实际故障探针均写在本工作区 temp 内；可重复的行为断言位于实验 4–6。临时探针清理后，不将它们当作永久实验引用。当前验证环境为 Windows、Node.js 24、pnpm 11；其他平台尚未实际运行。

### 收益与成本尚不能混淆

已证明的是：同一调用入口能发现任务、给出调用示例、阻止未授权执行、保存部分结果并在修正后重跑；新增一个普通函数任务无需修改 CLI。**尚未测量**人工接洽时间是否下降，也未证明这两个包优于针对单个脚本的直接调用。

付出的成本是额外的描述、授权字符串、步骤标记和两个包的维护。当前包边界表达的是“通用可信调用”与“工作区/pnpm 语义”的分离，尚未经过第二类设施检验；不应把能够运行误当作通用性已经成立。如果后续任务只增加元数据而不降低接洽成本，应缩小目录适用范围，而非继续添加框架能力。

## 必须保留的限制

- 模块是可信代码，list/show 导入模块时也可能产生副作用；调用前的授权检查不是模块加载沙箱。
- 权限和副作用是协作声明，无法约束脚本实际访问哪些文件、网络或子进程；只对已知可信本地任务授权。
- 每次重新读取配置避免使用内存中的旧配置，但不是原子快照；读取后到实际执行之间仍可能发生变化，不能宣称消除了所有 TOCTOU 问题。
- 步骤证据只记录实际观察到的结果；成功退出不证明任务语义正确，失败也不证明没有副作用。
- 返回结果由调用方持有；无自动持久化、永久历史、断点续跑或通用经验检索。线索没有经过再次验证，不能升级为永远适用的规则。
- 新包与 `src/` 中历史原型不构成兼容层。旧实验保留其可追溯性，但不要求新实验使用旧抽象。

## 对旧命题的证据范围修正

[第一轮摘要](1-core.md#结论摘要)中“身份只在跨序列化/恢复边界时值得注册”超出了当时实验能证明的范围。本轮工作区任务没有引入身份注册，说明路径和模块引用足以完成**这条任务**；这既不否定其他身份机制用途，也不足以证明所有非恢复场景都无需身份。旧结论保留，引用时应附带该限定。

## 研究前沿

下一步优先接入另一条不同接口的真实工程任务，观察新增描述与适配成本，而非扩大任务框架。尤其需要反例来检验：显式注册是否只是给原有脚本增加重复元数据；部分结果是否真的帮助了后续判断；配置证据是否足以识别误用。只有重复需求被不同情境验证后，才考虑共享机制。

明确不实现统一实体图、自动插件发现、响应式依赖传播、工作流调度、安全沙箱和通用经验引擎。
