# 发布标签一致不等于构建源码已绑定

本轮针对[范围结论4](4-infrastructure-scope.md)中的CI/CD、真相与契约管理、配置与可迁移性问题，不检查业务功能。[案例1](../cases/1-heterogeneous-engineering-workspace.md)中的[整合与组合](../cases/1-heterogeneous-engineering-workspace.md#32-整合与组合)、[变化与演化](../cases/1-heterogeneous-engineering-workspace.md#34-变化与演化)是问题背景。`commit` 引用包含实验、实现和本结论的标签 `5-release-lineage`。

## 实际操作问题

一次流水线已成功，运行端也报告预期的发布标签与源码提交：现在是否有足够证据声称“目标正在运行该提交构建的内容”？如果没有，应补什么，而不是继续重跑部署？

普通工具已能读取Git、CI状态、Release元数据和HTTP响应；缺口在于这些证据原本由人工串接，且**元数据中的同一个值可能都来自同一事件参数，并非彼此独立的验证**。

本轮交付 `@locus/deployment-audit`，将四项判定显式化：发布标签、声明提交、构建现场revision/dirty、制品与运行payload的SHA-256。仍使用普通对象与函数，不引入实体图、契约DSL或部署引擎。

## 实际只读调查：有绿色信号，但证据链不完整

匿名化的[现场摘要](../evidence/5-release-lineage/field-observation.json)记录：

- CI接口报告相关运行完成且成功；运行端声明的提交与所审查发布标签的提交匹配。
- 静态检查发现构建使用固定工作树，没有在已审查构建步骤中从事件提交检出；打包时写入的sourceRevision来自CI事件参数。
- 本次未取得实际制品内容和当时的构建现场见证，未读取运行payload。因此不能确定实际构建源码，也不能把CI成功升级成完整一致性保证。
- 所审查发布是运行目标自报版本对应的发布；用户意图发布的版本未另行给出，不能宣称满足了独立的目标版本要求。

实际CLI审计返回 `incomplete`，不是“部署错误”，也不是“允许发布”。未修改真实流水线、服务或机器。

**公开证据边界**：摘要删除了真实工程、主机、地址、标签及源码提交，公众无法据此独立重放私有现场。本节属于已观察事实的脱敏记录；下面的受控实验才是公开可复现的反例。不能把两者混为一项现场故障证明。

## 错误假设与公开反例

**原假设**：事件触发提交A，CI成功，制品/运行端均写A，健康检查通过，即可认为实际构建来自A。

**为什么不成立**：固定工作树可能已经位于B；如果打包脚本只是把事件SHA写进release元数据，A这个字符串就会跨越多个环节原样传播。后续再核对这个字符串，可能只是在确认复制链没有改字，而不是源码绑定。

[实验10](../../tests/10-source-binding/demo.test.js)真实创建Git提交A/B，保留工作树为干净的B；复制B的payload生成制品，仍把A作为声明传给HTTP运行目标。服务器健康检查返回200，标签与声明提交一致，制品与运行payload也一致，但构建现场见证指向B，评估为 `mismatch`。制品payload与从A生成的payload实际不同。

这不是简单让执行器抛错来证明错误处理：原有绿色判断在错误内容下仍成立，被否定的是“这些绿色信号足够证明构建源码”的工作假设。它复现私有调查所暴露的机制风险，**不证明私有现场当时真的构建了B**。

**修正**：在工作区内干净检出A，重新复制实际payload并生成见证，再交付、读取和比较运行字节。不是只改标签，也不是重部署原错误制品。

| 场景 | 健康/标签信号 | 构建与内容证据 | 结论 |
| --- | --- | --- | --- |
| 实际只读调查 | CI成功、运行声明与标签匹配 | 未取得实际制品、构建见证及运行payload | incomplete，不作完整发布保证 |
| 受控错误构建 | 健康200，标签与声明均匹配 | 工作树为B，而期望A；运行字节来自B | mismatch，拒绝按原条件放行 |
| 干净检出A后重建 | 健康200，标签匹配 | 构建见证为A且clean，制品与运行payload一致 | consistent，仅限已检查契约 |
| 同一修正制品交付新角色 | 健康200，标签匹配 | 重新取得新目标的HTTP内容，不复制旧观测 | consistent，不证明跨物理机器 |

## 可使用的结果与下一步动作

- `assessRelease` 的每项结果为 `pass/fail/unknown`；任一已证冲突优先 `mismatch`，否则缺证据为 `incomplete`，全部通过才 `consistent`。
- 缺失、空白或非法值不因彼此相等而算通过。声明提交不能填补构建见证；元数据自报hash不能填补实际payload读取。
- `readGitSource` 实际采集HEAD与dirty，未跟踪文件计入；要求dirty显式false，而不是仅比较提交字符串。
- `observeRelease` 读取有时限/体积限制的HTTP证据；hash基于完整响应原始字节，不基于解码文本或release元数据。BOM等编码差异不会被静默丢掉；截断与中断不产生完整digest。
- 原有工作台增加 `deployment.audit`，需要显式授权。审计执行成功只说明报告已生成，**外层退出0不能当作发布门禁**；需读取 `value.assessment.verdict`。
- 遇到源码见证冲突，应从期望提交的干净工作树重建并重新取证；不能靠修标签或重跑部署恢复源码契约。遇到缺证据，应先补证据，而不是指控运行版本错误。

## 对日常工作的实际帮助与代价

该包现在可以用于发布核对和联调：保留“哪些已经一致、哪里有冲突、哪里只是没证据”，避免人工把健康与版本字符串拼成过强保证。同一制品交付新目标时可复用制品证据与判定规则，但必须重新获取运行事实。

[实验8](../../tests/8-http-evidence/demo.test.js)验证传输中断、伪JSON/HTML回退、实际字节hash与重新观测；[实验9](../../tests/9-release-contract/demo.test.js)验证判定边界；[实验10](../../tests/10-source-binding/demo.test.js)贯通真实Git、文件交付、HTTP目标和判定。不是仅验证字段转发。

未测量人工节省时间，也未把门禁接入真实部署。代价是需要构建器和取证方提供独立的源码/内容见证；仅增加字段而继续复制事件值，不会得到新保证。包目前是受信工程协作工具，不是证明系统或来源认证服务。

## 契约边界与未决问题

- Git clean只描述Git可见工作树，不覆盖被忽略配置、环境、依赖、工具链或构建期间变化。dirty违反本轮clean契约，但不必然意味着payload字节不同；clean也不保证可重复构建。
- 构建见证是调用方提供的受信事实，没有签名与认证；本包不能阻止伪造见证或hash。
- 这里只比较一个指定payload；不证明整个制品、全部部署目录或实际进程所加载代码一致，也不证明业务正确。
- 元数据与payload分次获取，不是原子版本快照；部署切换期间仍可能读到混合结果。暂不增加版本固定读取或重试来掩盖这个缺口。
- 同机目录和临时HTTP目标没有验证跨物理机器网络、凭据、TLS、权限与工具链迁移。公开演示只覆盖角色迁移与重新取证。
- 私有制品与完整构建现场仍未取得；不将接口未提供的证据解释为制品不存在。

下一步优先验证配置/工具链条件如何进入构建见证，以及在实际目标上如何固定版本取证；不要先搭完整CI平台或通用真相引擎。该方向支持[结论3](3-operational-experiments.md)对完整工程任务和研究性反例的要求，同时遵守[结论4](4-infrastructure-scope.md)的范围与公开边界。

## 复现

```sh
pnpm install --offline --ignore-scripts --frozen-lockfile
pnpm demo:release
pnpm test
pnpm locus show deployment.audit
```

`demo:release` 会创建并清理工作区内临时资产。现场身份和脱敏映射不进入仓库；本结论的tag只用于复现公开实验，不赋予对私有现场的访问能力。

本轮实际运行：`pnpm test` 77项通过、0失败；`pnpm demo:release` 得到错误构建 `mismatch`、修正后 `consistent`、新目标角色重新观测 `consistent`；离线 frozen-lockfile 安装通过。实际 CLI 的只读现场审计为 `incomplete`，未将缺证据当作绿色发布结果。
