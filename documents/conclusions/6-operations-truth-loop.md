# 从配置故障到证据化运行手册的全流程

`commit` 引用包含实现、实验和本结论的标签 `6-operations-truth-loop`。本轮是[案例1](../cases/1-heterogeneous-engineering-workspace.md)中组合已有能力、处理失败、知识修正和跨情境复用的一条可执行闭环，遵守[范围与公开边界](4-infrastructure-scope.md)。不使用真实工程、生产端点或私有身份。

## 实验任务与实际边界

任务：完成服务A的交付验收；请求失败时辅助定位原因，实施并验证修复，再更新运行手册，使第二个实例能利用该记录。

[实验11](../../tests/11-operations-loop/demo.test.js)实际使用Git、文件、独立Node子进程与HTTP。基础设施有活动后端、退役后端和网关角色；端口由系统分配，角色登记、实例替换、进程停止均真实发生。CI阶段执行源码语法检查、采集Git见证并生成制品；CD阶段复制制品和目标配置，启动进程。这里是本地流水线，不是外部CI服务器，也不是跨物理机器部署。

配置有两个实际文件：`config.json` 是目标基础配置，`environment.json` 是部署环境覆盖层。子进程在启动时读取，后者优先。**这不是操作系统环境变量或秘密管理的验证**。制品与目标配置分开交付，同一制品可以对应不同运行行为。

## 本次完整路径

1. 登记并启动活动后端、退役后端与网关。退役后端仍响应健康检查，但功能接口返回410，避免用随机“空闲端口”制造不确定故障。
2. Git源码检查及制品交付通过；独立读取网关实际payload，发布审计为 `consistent`。
3. 网关健康检查200，但真实 `/check` 返回502：环境覆盖把正确文件配置指向退役后端。
4. Debug先核对源码/交付字节，再直接探测活动后端，结合有效配置及其来源，形成“环境配置覆盖”的假设。此时不把假设标成已证实事实。
5. 清空环境覆盖文件；活进程仍502，证明“文件已修改”不能代替“进程已采用配置”。重启后有效配置来源变为file、请求200，且制品未重建。
6. 把原判断、修正、干预前后证据、哈希和适用条件实际写进 `knowledge/runbook.md`。保留原文，并明确原判断在条件内已被修正，不再作为有效操作规则。
7. 将实际手册和证据提交到隔离的临时Git仓库，再用 `core.autocrlf=true` 克隆。向另一网关角色交付同一制品，复现同类配置故障；重新观测该实例，从**克隆后的Markdown与证据**检索适用记录，选择预定义处理方法。不重复构建或额外直接探测活动后端，仍执行修复与请求验收。
8. 停止并等待全部子进程退出；演示保留证据和文档，自动测试清理自己的临时目录。

## 观察结果

| 观测阶段 | 发布字节审计 | 请求 | 可以得到的判断 |
| --- | --- | --- | --- |
| 初次交付 | consistent | 502 | 发布一致性不能代替端到端就绪 |
| 清空环境文件，未重启 | 制品未变化 | 502 | 磁盘期望与活进程配置仍不同 |
| 重启后 | consistent | 200 | 在本次条件内，覆盖清除并重启后恢复 |
| 第二个实例复用文档方法 | 复用同一制品，新实例重新观测 | 200 | 知识确实参与动作选择，而非仅追加日志 |

全流程只构建一次；首次debug有一次额外的活动后端直接探测，复用阶段没有重复该探测。未进行时间收益基准测量，不把这些操作差异外推为效率提升比例。

## 被否定或限定的判断

- **“健康与版本/字节一致就代表可用”——被反例否定。** 同一进程健康200、发布审计一致，业务无关的测试请求仍502。这里限定[结论5](5-release-lineage.md)的保证范围，不推翻其四项发布证据检查。
- **“改对文件即可恢复”——在本配置模型内被否定。** 环境覆盖优先且启动时加载；清空文件后，未经重启的进程仍使用旧值。修复是清除覆盖并重启、再验收，而不是特殊处理502或让异常变成功。
- **“追加一条经验就值得信任”——不能成立。** 记录必须有真实证据、明确条件，使用时复查字节与有效期。哈希只证明引用的字节一致，不证明作者的语义判断正确。
- **“记录了修正就可以无条件推广”——被限制。** 制品SHA或配置模型改变时不复用；[实验12](../../tests/12-evidence-notebook/demo.test.js)还验证证据改动、丢失、过期和坏记录的失效行为。
- **“证据文件经过Git检出仍是相同字节”——本轮方法探针否定。** 未声明策略时，`core.autocrlf=true` 把LF改为CRLF，证据字节随之变化；声明 `documents/evidence/** -text` 后相同探针保持字节一致。本仓库采用该策略，全流程又实际提交、克隆并重查证据。修复的是发布/检出契约，不是在哈希校验时忽略差异或放宽真相条件。

这是受控配置事故，不宣称在真实环境发现了同类生产故障。诊断是可解释的领域规则，不是LLM通用debug能力证明；干预结果只支持当前条件下的修正。

## 实际文档，而不只是结论报告

可对照本次实际生成的[原始手册](../evidence/6-operations-loop/knowledge/runbook.before.md)和[修正后手册](../evidence/6-operations-loop/knowledge/runbook.md)，以及它引用的[故障证据](../evidence/6-operations-loop/evidence/incident.json)、[修复证据](../evidence/6-operations-loop/evidence/repair.json)、[第二次处理证据](../evidence/6-operations-loop/evidence/repeat.json)。[基础设施快照](../evidence/6-operations-loop/infrastructure.json)、[执行轨迹](../evidence/6-operations-loop/events.json)与[摘要](../evidence/6-operations-loop/summary.json)来自同一次运行，复制公开快照时已逐一校验手册内的证据哈希。

公开快照是历史记录，包含有时效的知识和已停止的本机实例，不是永远有效的在线状态声明；重新运行演示会生成新的现场和时效。仅使用匿名角色、回环地址与本实验生成的标识，不含真实项目映射。

新增 `@locus/operational-knowledge` 提供 `appendFinding` 和 `findApplicableFindings`。它以单Markdown文件保留手写原文，追加人读修正和可解析记录；证据校验失败不改文档，成功时同目录临时写入并rename。查询时重查条件、到期时间及文件哈希，不维护平行知识库。

步骤ID用于选择实验内固定的允许操作，不执行文档中的任意命令。这是人和Agent可读取、审查、复用的操作记录，不是自动推导真理或通用工作流引擎。

## 对实际工作的帮助与成本

这条链把“该回滚代码吗”“配置改了为什么无效”“旧手册还能不能用”转成有证据边界的判断：先看交付和有效配置，保留假设，实施有边界的干预，再把可复用修正写回项目知识。

没有把所有基础设施提升成统一核心类型。进程管理与交付仍留在实验内，复用已验证的发布审计包；新包只沉淀本轮需要的文档/证据绑定。其成本是生产方必须暴露足够的配置来源信息，操作者必须采集并保留证据，而不是只写一句成功经验。

## 剩余限制

- 角色是同机独立进程；未验证跨主机网络、TLS、凭据、服务管理器或真实CI平台。
- 发布审计仍只绑定指定payload，不覆盖全部配置与依赖。配置诊断来自受信演示服务，尚无远端来源认证。
- 笔记本不证明语义蕴含，不自动解决多个互相矛盾的修正或重复ID，也没有并发追加锁；哈希校验与读取之间仍有TOCTOU。
- 条件仅包含当前制品与配置模型；它们不是全部适用条件的普遍答案。新的实例仍需现场检查与修复验收。
- 证据字节恢复后可重新通过校验；历史快照不等于当前环境事实。人工改动机器记录或伪造证据不能由该包自动识别为欺骗。
- 整体演示中的文件替换不是一项覆盖所有资源的事务；文档的单文件原子更新也不意味着整个交付/排障流程原子。

## 运行与验收

```sh
pnpm install --offline --ignore-scripts --frozen-lockfile
pnpm demo:operations
pnpm test
```

演示输出 `artifactDirectory`，其中保留实际运行手册、JSON证据、配置文件、制品、执行轨迹，以及知识的临时Git仓库和克隆；进程均已停止。目录在工作区 `temp/` 下并被Git忽略。自动测试默认清理自己的实例；不会清理用户保留的其他演示目录。

本轮实际验收：`pnpm test` 84项通过、0失败；完整程序输出请求502→修改文件仍502→重启后200，文档修正、Git克隆后复用、制品变化失效与全部资源停止均通过。离线 frozen-lockfile 安装通过；公开快照复制时的证据哈希也已验证。验证环境为Windows、Node.js 24、pnpm 11，其他平台尚未实际运行。
