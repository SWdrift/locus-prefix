# 共在与流畅的历史路径：从活系统、组合接口到可演化的语义边界

关联[案例1](../cases/1-heterogeneous-engineering-workspace.md)、[结论9](9-workspace-evolution.md)、[结论10](10-semantic-boundaries.md)、[范式研究](../paradigm-study.md)及[执行与互操作研究](../execution-history-study.md)。本结论为**事实型文献研究**：核对原始论文摘要、作者/项目一手文档、官方标准及已有仓库记录；未新增实验、运行外部项目、修改旧结论或测量真实生产成本。以下将**文献事实／既有实验观察／综合推论／待验证假设**分开，不把来源作者的愿景当作已实现的普遍保证。

## 1. 问题修正：流畅不是“能用代码表达一切”

[案例1](../cases/1-heterogeneous-engineering-workspace.md)要求异构设施在保留原有语义和生命周期的同时逐步建立联系。[结论10](10-semantic-boundaries.md)进一步证实：CRDT合并、派生判断、事务接纳和外部动作有不同的保证边界。后者回答了**不应混淆什么**，还不足以回答**什么样的组合真正减少接洽成本**。

新研究问题因此不是“需要哪一种统一图或执行器”，而是：

> 当代码、文档、GIS服务、机器、工具、人员和Agent各有自己的身份、历史与权威来源时，怎样让它们跨越必要的边界而不丢失完成任务所需的意义、保证和修改能力？

此处的“语义连续性”仅为**候选研究用语**：消费者能在相邻的发现、理解、组合、执行、复核步骤中，识别使用了什么对象/版本/证据、哪些信息被转换或丢弃、谁对结果负责；它**不**要求所有对象同构、所有状态自动同步或所有修改可撤销。尚无单一指标或实现证明这是一种新的范式。

## 2. 四种不同的历史答案

### 2.1 活系统：把使用、观察和修改放在同一环境

**背景与事实。** Alan Kay 在《[The Early History of Smalltalk](https://doi.org/10.1145/155360.155364)》（1993）的摘要中回顾了消息、个人计算和学习环境的共同目标；这不只是后来意义上的类继承。Self 的《[The Power of Simplicity](https://bibliography.selflanguage.org/self-power.html)》（1987）明确以原型、槽与行为缩小对象、过程、闭包之间的距离。Self 的[手册](https://handbook.selflanguage.org/2024.1/intro.html)将 simplicity、concreteness、liveness 作为语言和环境的共同目标；Morphic 的《[Directness and Liveness](https://bibliography.selflanguage.org/directness.html)》（1995）则把直接指向对象即可检查、修改，以及对象持续响应，列为环境特性。

**获得与代价。** 这些系统证明“描述、运行、检查、修改”可以比常见的编辑—构建—启动流程更贴近；但这种直接性建立在强环境约定与可检查的对象世界之上。论文和手册并未证明任意SSH目标、GIS服务、外部数据库也自动进入同一生命周期。把外部状态投射进活环境仍需接口、失效规则和副作用控制。

**对原‘言灵’推断的限定。** JS/TS 对象与函数可以是有用的描述/执行媒介，但“同一语言”不等于“同一活世界”，更不等于跨设施真相一致。活系统是一条有效竞争路线，不是应当被原生模块方案默默吸收的语法风格。

### 2.2 Unix：不共享对象世界，也可以获得极强组合性

**背景与事实。** 贝尔实验室的[Unix历史访谈](https://www.nokia.com/bell-labs/unix-history/philosophy.html)指出，管道使小工具“相互协作、处理文本流”的取向逐渐具体化。重要创新不是预先知道所有可组合程序，而是让未来尚未知晓的生产者和消费者能沿稳定边界连接。

**获得与代价。** 共同的流/进程接口降低了临时组合成本；但管道不传递任意领域对象身份、事务边界、权限或GIS坐标系含义。结构化约定、错误处理、重试和外部效果仍由上层负责。它不是“无契约组合”，而是**把契约缩窄到足够通用的局部接口**。

**竞争意义。** 一套显式 JS/ESM 模块、原生进程和成熟协议的联邦工作空间，可能在大量短期任务中比统一图/注册表更流畅；[结论9的Agent组合](9-workspace-evolution.md)为局部可行性提供既有实验支持，但尚无跨长期任务的成本比较。

### 2.3 Unison / Denicek：历史可以是计算模型的一部分，不只是审计附录

**背景与事实。** [Unison 的核心设计](https://www.unison-lang.org/docs/the-big-idea/)使用定义语法树的哈希作为代码身份，名称作为独立元数据；[Codebase Manager 的历史/撤销机制](https://www.unison-lang.org/docs/usage-topics/resetting-codebase-state/)把代码定义与变更管理纳入语言工具链。由此可支持不改变定义身份的重命名，以及对依赖定义的结构化追踪。代价是特定语言、代码库格式、迁移和工具生态；定义哈希并不能为外部机器或数据库赋予可靠身份。

2025 年 Petříček 与 Edwards 的《[Denicek: Computational Substrate for Document-Oriented End-User Programming](https://www.d3s.mff.cuni.cz/publications/petricek_denicek_2025/)》提出另一种有力反方：把程序表示为构造/变换数据与公式文档的一系列编辑，基于编辑应用、历史合并和冲突解决组合出多种交互式编程体验，并以交互式数据科学笔记本作为案例。这里依据作者机构提供的**论文摘要**，未复核全部实现与性能数据。

**竞争意义。** “统一历史/更强计算基底”不能因为 Core 偏好轻量就被提前排除。它们可能将多个使用者反复承担的变化责任收束到同一个 substrate；是否划算取决于任务是否真正处在该 substrate 的语义范围内。它们也不能由此推出外部执行器的安全性或异构设施统一身份。

### 2.4 Cambria：先统一所有版本，反而可能妨碍未来演化

**实际失败与修正。** Ink & Switch 的《[Project Cambria](https://www.inkandswitch.com/cambria/)》（2020）使用双向 lens 组合异构 Schema，并与 Automerge 做原型集成。作者明确记录了一个被放弃的方案：**写入时主动转换到全部已知 Schema**。该方案无法处理未来才出现的新 Schema，也难以处理写入与注册 Schema 并发的情况，还带来不必要的预先转换成本。团队改为保存写入者 Schema 下的原始变更，在读取时按目标 Schema 转换。

这不是“所有数据都应懒转换”的证明。作者同时指出，双向转换存在不可逆信息问题；某些复杂转换、跨文档修改、缺失外部数据及性能仍未解决。Cambria 是研究原型，不能当作已经全面验证的生产级互操作层。

**对案例1的意义。** 在旧 GIS 配置、新服务接口和未来数据结构并存时，提前制造一份唯一的“当前统一格式”可能增加同步债务。保留源格式、版本和转换责任，按需产生消费者视图，是值得与一次性迁移/规范化比较的**条件性候选**；坐标系、单位、缺失字段和只单向成立的转换必须作为领域规则明确表达。

## 3. 两类能改变问题定义的公开实践

### 3.1 可塑软件：流畅首先是实际使用体验，而非最短API

Ink & Switch 的《[End-user Programming](https://www.inkandswitch.com/end-user-programming/)》（2019）综合 Unix、电子表格、Smalltalk 等经验，提出具身表达（embodiment）、活系统（liveness）、原位工具链（in-place toolchain）三个研究特征。其 Capstone 原型既有正向发现，也有**具体失败**：可视化计算卡片会变乱；最好的 REPL 原型仍依赖外部工具链；公开 API 与文档设计成本巨大。2025 年的《[Malleable Software](https://www.inkandswitch.com/essay/malleable-software/)》延续了“用户能在使用现场修改工具”的目标，而没有宣称一个通用基底已解决它。

[Webstrates](https://webstrates.net/)（首篇论文发表于2015年）展示另一条路线：通过可协作的 DOM，让HTML/CSS/JS内容及部分应用结构能够在运行时修改并同步。但这依赖其特定的Web文档环境，不能推导为所有外部设施都有活修改能力。2025 年的 Denicek 则证明研究者仍在探索“先建设强计算基底，再提供新交互”这条方向。

Alex Warth 在 2026-09-14 的《[Effective Expressiveness](https://www.inkandswitch.com/malleable-software/effective-expressiveness/)》区分了理论上能表达与实际自然地表达，强调成本随**语言、任务与使用者**变化。这是作者提出的分析视角，不是已形成严格度量的定理。它对本项目的直接提醒是：不应以 JS 图灵完备、函数调用简短或减少 Core 类型数证明“流畅”。

**候选测量对象**：完成任务时需重新发现多少上下文、写几次转换、多少步骤可直接检查与局部修改、哪些假设需人工解释、改动后重新验收的范围，以及任务出错后能否准确恢复认识。Agent 生成代码所省时间与新引入的验证/审查责任应同时计入。

### 3.2 GIS与运维标准：成功的互操作经常是有边界的，而不是普遍统一

[OGC WMS 标准](https://www.ogc.org/standards/wms/)提供请求地图影像的共同HTTP边界；[OGC API – Features](https://www.ogc.org/standards/ogcapi-features/)将资源发现、数据集集合、要素查询及更多可选能力分为模块化的标准部分。它们使不同供应商的 GIS 系统在**特定操作**上互操作，并不规定远端服务部署、许可、数据库迁移或真实状态变更。坐标参考系及轴顺序等问题仍属于协议版本和领域语义的一部分。[实验14](../../tests/14-workspace-evolution/demo.test.js)只实现过受限WMS替身，不能冒充通用OGC兼容认证。

[Terraform 的 refresh-only 工作流](https://developer.hashicorp.com/terraform/tutorials/state/refresh)则允许观察漂移并更新 state，而不立即修改远端设施。它通过显式区分期望配置、记录状态和提供者观测，换取可检查的协调过程。与[结论5](5-release-lineage.md)、[结论6](6-operations-truth-loop.md)的构建见证及进程采用证据相吻合：**知道、期望、声明和已经生效不是同一事实**。

这些是有限互操作与强约束管理的正面证据。反方也应保留：Nix 的依赖闭包、Temporal 的[事件重放与Activity边界](https://docs.temporal.io/workflows)等通过相对复杂的引擎承担跨版本或崩溃恢复责任，可能比重复拼接轻量接口的总体成本更低；详细机制及未运行限定见[执行专题](../execution-history-study.md)。

## 4. 历史交叉后可以保留的五项判断

下表是**由外部机制和本仓既有实测支持的有限结论**，不是五条核心类型定义：

| 判断 | 支持与反方 | 边界 |
| --- | --- | --- |
| **共在不要求同一对象世界。** | Unix管道、OGC协议及案例1的领域模块都能让独立设施协作；Self/Webstrates则展示共同活环境在特定范围内的价值。 | “无统一世界”不等于“无共同接口”；跨域组合仍需明确语义及权限。 |
| **描述与执行相邻，不保证事实与动作相同。** | 活系统缩短修改反馈链；Terraform、Temporal、实验14–16暴露外部状态、重放和副作用的独立责任。 | 不因此否定代码即工作描述，也不要求永远分离两者。 |
| **历史的单位依赖想保留的性质。** | Git保存提交树，Unison保存定义/命名历史，Automerge保存因果变更，Denicek用编辑历史构成计算基底；实验15验证普通JSON投影丢失因果保证。 | 不推出统一历史不可能；任何投影都须说明保留/丢弃的保证。 |
| **按需转换可以降低演化耦合。** | Cambria撤回预先多Schema写入方案；WMS/OGC沿协议边界提供特定互操作。 | 不可逆转换、执行副作用、协议失效和动态查询可能使延迟转换不合适。 |
| **流畅必须按任务与使用者评价。** | Ink & Switch 的原型失败、有效表达视角、结论8/9对短API成本推断的撤回。 | 目前没有跨方案、长期、人/Agent参与的等价成本数据。 |

**综合推论（未证成普遍原则）**：Locus Prefix 可以优先把研究单位从“对象/图/任务类型”转为**跨边界的意义与责任是否连续**。可能需要的不是统一持久化世界，而是针对当前任务可追溯的源、身份、版本、转换、观测、判断和动作契约；但若这些关联反复要求同一类计算与历史保证，强共享基底也可能更便宜。

这不是让 `source/version/contract/...` 立即成为通用元数据结构。它们是检查语义断裂时的问题清单，不是数据模型。

## 5. 原判断的修正及保留的竞争方向

- **“JS/TS 能描述并执行，因此应成为系统的统一世界”——限定。** JS/TS 仍适合大量局部组合，但外部资源真相、并发历史与恢复语义并不由语言自动提供；Self/Unison/Denicek/Nix 等是基本语义不同的竞争方案。[结论10](10-semantic-boundaries.md)已撤回 JS 中心的普遍必要性，本轮给出历史上的建设性替代例证。
- **“实现统一对象目录会让接洽更流畅”——未证。** 对于稳定内部对象可能成立；Unix、OGC和Cambria给出了保留独立来源、按需接合的强基线。需要证明总体成本收益，而不只展示一次查询或漂亮的关系图。
- **“简单Core天然成本最低”——未证。** Ink & Switch 的API/工具链失败和 Denicek、Temporal 的强基底形成反方。比较须包含消费者承担的重复责任、复杂引擎的迁移/运维代价，以及调试和安全边界。
- **“区分探索、判断、动作就足以带来流畅”——不成立为充分结论。** [结论10](10-semantic-boundaries.md)的三类责任有实验支持，但 Ink & Switch 的体验研究提示还必须观察原位修改、可见反馈、上下文保留、适配成本。三层语义正确不等于使用过程自然。

可继续竞争的至少有四条路线：联邦式原生模块/协议组合；共同活对象或共享文档环境；以编辑/因果历史为计算基底；由构建、协调、工作流与能力运行时承担保证。它们各自可能更适合不同的任务阶段或子系统，不预设只能选一个赢家。

## 6. 下一步的区分性问题（不是新架构清单）

1. **同一 GIS 设施发生接口/Schema/目标迁移后**，是保留原始事实并在读取时适配、统一迁移模型，还是靠已有协议直接重新发现，能够以更少的总成本维持正确消费？须包括不可逆转换、旧客户端及错误路径；不能只比调用行数。
2. **同一 Agent 工作任务跨三个版本继续执行时**，保留临时 JS 组合、内容/定义寻址及编辑历史基底，哪种真正减少重新建构上下文和误用过期证据？需记录人类审查、恢复和调试成本，而不单独计算 token 数。
3. **离线反证抵达且已有意图待执行时**，在同一领域不变量下比较版本前提执行与有限授权/不变量保持操作。该分歧仍由[结论10](10-semantic-boundaries.md)提出；本轮历史研究既不解决它，也不将它当唯一未来方向。
4. **活环境/统一基底是否更值其成本**：选一个必须经历多次观察—修改—复核循环的实际任务，对比联邦脚本、专用活环境及成熟协调引擎，要求相同外部效果、安全边界和故障注入，再评价体验和维护总成本。

**淘汰条件**：如果上述问题采用现有协议、普通函数及少量记录即可低成本地持续完成，则无需新增 Locus Core；如果多种独立任务反复被同一种历史、转换或执行责任拖累，并证明共用机制降低总成本，则应认真研究强共享基底，不受“简单Core”偏好阻止。

## 7. 证据覆盖与限制

- **已核对的一手历史/项目资料**：Smalltalk 1993 论文摘要；Self 1987 论文摘要、1995 Morphic 摘要及手册；贝尔实验室Unix口述史；Unison 官方设计与历史文档；Cambria 2020 原型作者全文及失败复盘；Ink & Switch 2019/2025 研究记录和2026有效表达笔记；Webstrates 官网；Denicek 2025 作者机构摘要；OGC 官方 WMS/API Features；Terraform 官方 refresh-only 文档；Temporal 工作流文档。来源均以内嵌链接对应本节相关断言。
- **本仓既有可复现证据**：[实验14](../../tests/14-workspace-evolution/demo.test.js)的受限GIS/Agent组合，[实验15](../../tests/15-causal-history/demo.test.js)的因果冲突与投影丢失，[实验16](../../tests/16-derived-decisions/demo.test.js)的图外更新及执行器边界。它们此前已运行、结论已记录；**本轮没有重新执行**，也没有新建 `tests/17-*`。
- **没有证据支持的外推**：各历史方案在现代 GIS 生产设施上的兼容/可靠性、复杂系统的长期总成本排名、Agent 真实使用时间改善、强基底已自然解决跨物理设施副作用；均保持待验证。
- **研究缺口**：未深入拆解 Smalltalk/Unison/Denicek 的完整实现、Webstrates 的安全模型、跨Schema双向变更的形式定律与各方案大规模部署失败史；这些是有价值的潜在反方，不能因本次综述未覆盖就将其判定为不可行。

**本轮结论**：历史既支持“共同活世界”的直接性，也支持“独立系统通过窄接口组合”的可扩展性，还支持“以强历史/执行基底吸收复杂责任”的路线。它们不属于单一演化序列。对于 Locus Prefix，更有根据的研究方向是：在具体任务中寻找跨边界的语义断裂，比较**消除断裂的收益**和**维持接口/转换/历史/执行保证的总成本**，并检验结果是否真的让人和 Agent 更流畅地共同工作；不预先决定是否需要新的独立系统。
