# 案例 A：持续演化的软件生产系统

## 1. 用途

案例 A 是 Locus Prefix 的长期实验问题域，用于探索轻量、可演化的 JS/TS 元系统。

案例 A 描述一个持续运行、不断变化的软件生产系统。用户和 Agent 可以定义对象、函数、引用、操作、知识及扩展，并在系统运行过程中发现、组合、解释、追踪和复用它们。

本案例不是待实现的产品规格，也不要求系统最终成为一套完整的基础设施管理平台。它提供具有一定规模、真实约束和复杂交互的问题环境，使实验能够逐步揭示有价值的机制、必要的不变量及其适用边界。

## 2. 基本世界

系统包含开发、预发布和生产环境，以及分布在不同机器上的服务和资源。

初始规模可以参考以下范围，但不要求一次性构造全部内容：

- 12 台机器，分布于 3 个环境。
- 10 个服务，涉及数据库、缓存、消息队列、对象存储及外部 API。
- 3 条 CI/CD 流程，涉及制品、部署、健康检查、迁移和回滚。
- 15–25 个可调用操作，包括自动化操作、检查函数和需要人工介入的操作。
- 多名维护者、多个 Agent，以及定义自身规则的扩展。
- 持续积累的配置变更、运行观测、操作记录、事故报告和经验结论。

上述数量仅用于控制案例的初始规模，不是必须满足的验收指标。实验可以按需增加、删除或简化对象。

系统中的对象不必服从统一的领域模型。机器、服务、配置、函数、凭据、观测、操作和知识都可以由普通 JS/TS 对象、函数、模块或扩展定义。它们不必全部进入同一种数据结构，也不必全部被系统自动发现或追踪。

## 3. 世界中的基本事实

案例应允许以下情况自然发生：

1. **对象与身份**：同一对象可以拥有多个引用或名称；同名对象可能属于不同环境；对象可以被替换、迁移或删除。
2. **共享与嵌套**：多个对象可以引用同一个对象；对象可以包含嵌套结构、数组、Map、Set、访问器属性及函数闭包。
3. **动态行为**：对象可以由函数生成；操作可以创建、修改或删除对象，也可以访问系统之外的资源。
4. **多种状态**：配置表达期望状态，观测描述某个时点的观察结果，操作记录描述实际发生的行为。三者可能不一致。
5. **不完整信息**：观测可能过期、缺失或相互矛盾；外部资源可能在系统无法观察的情况下发生变化。
6. **非原子操作**：一个操作可能包含多个步骤，部分步骤成功后发生失败；外部副作用不一定可以撤销。
7. **并发与冲突**：多个维护者或 Agent 可以基于不同的状态、知识或假设执行操作，并产生相互影响的变化。
8. **扩展与异构契约**：不同扩展可以定义自己的对象结构、解释规则、操作接口和副作用，不要求它们具有相同的领域语义。
9. **知识演化**：系统会积累成功经验、失败记录、推断、假设和修正后的结论。旧结论可能被新证据限制、修正或推翻。

这些是案例允许出现的情况，不是要求 Core 为每一种情况提供专门机制。

## 4. 持续演化的主线

案例以一次生产系统迁移及其后续事故作为可反复展开的主线。

### 阶段一：初始运行

系统拥有机器、服务、配置、部署操作及少量运行观测。部分对象存在共享引用，部分操作依赖外部资源。初始实现可以非常简单。

### 阶段二：资源迁移

数据库从机器 A 迁移到机器 B。相关配置、引用和观测陆续变化，但并非所有消费者都会立即获取最新信息。系统需要面对旧引用、对象替换和过期观测。

### 阶段三：部分失败

应用部署过程中，制品上传和旧实例停止已经成功，新实例启动却失败。与此同时，数据库结构发生变化，常规回滚不再安全。系统需要区分期望状态、实际状态、操作结果和已产生的副作用。

### 阶段四：协作与冲突

多个 Agent 根据现有记录提出不同的故障解释和修复方案。其中一个 Agent 修改了服务配置，使另一个 Agent 原先计划中的前置条件不再成立。观测信息也可能不足以唯一确定故障原因。

### 阶段五：修复与知识修正

系统执行部分修复并记录结果。事后分析发现，一项原先被接受的推断并不成立。相关结论需要根据证据修正，同时保留其原始依据、适用条件和历史关联。

上述阶段不要求按固定顺序一次性实现。可以从任意一个具体问题开始，也可以引入新的事件、对象或反例。

## 5. 实验原则

案例 A 的演化遵循以下约束：

- **需求驱动**：只有实验遇到具体问题时，才考虑增加相应机制或契约。
- **保持开放**：案例中的对象名称、分类和操作不构成 Core 的类型定义。不得仅因为案例中出现某种概念，就将其提升为核心抽象。
- **优先使用原生机制**：普通对象、函数、模块、闭包及 JS/TS 自身能力应作为可行基线。新机制需要通过实验说明其收益及成本。
- **区分事实与解释**：实验记录应区分可观察事实、设计选择、推断、假设和未验证结论。
- **允许失败与反例**：不预设某种机制一定适用。应主动寻找其失效条件、遗漏行为和额外复杂度。
- **渐进式扩展**：每次实验只引入足以验证当前问题的情境，不要求构造整个生产系统。
- **不提前统一语义**：领域解释、操作策略和特殊约束可以留在使用方或扩展中，不必为了统一建模而强行合并。
- **不将案例事实误作系统能力**：案例可以包含历史、引用、并发和副作用等复杂情况，但系统是否需要专门支持它们，必须由实验决定。

## 6. 与实验及结论的关系

案例 A 是长期稳定的问题域，实验是对其中具体问题的可复现探索，结论则是由证据支持的阶段性认识。

开展新实验时，应：

1. 指明所使用的案例情境及需要验证的问题。
2. 构造最小的可运行实例，优先验证机制边界而不是追求场景完整度。
3. 记录实际结果、失败情况、适用条件和剩余不确定性。
4. 将结论与对应实验、代码提交及相关旧结论建立可追溯的联系。
5. 根据新证据修正已有认识，不静默覆盖被修正的结论。
6. 从实验结果提出下一步问题，而不是预先执行一份固定的功能路线图。

案例本身只有在世界事实或问题设定确实需要调整时才应修改。实验发现的新知识优先写入结论文档，并通过链接与案例及其他结论关联，避免将案例变成所有实验记录的汇总文件。

## 7. 成功标准

案例 A 不以功能覆盖率、对象数量或最终架构的完整性作为成功标准。

真正有价值的结果，是通过连续、可复现的实验，发现某些能够跨越不同情境复用的机制，明确它们的保证、代价与失效边界，并判断这些机制应当留在具体使用方、成为可选扩展，还是有充分证据进入 Core。

如果实验表明，某个问题使用普通 JS/TS 机制就能以更低的成本解决，这同样是有效结论。

**案例 A 的目标不是证明 Locus Prefix 应该存在，而是持续检验它在真实复杂性面前究竟能提供什么不可轻易替代的价值。**
