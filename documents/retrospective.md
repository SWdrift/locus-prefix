# Locus Prefix 项目回顾：从共同媒介到有边界的组合

Locus Prefix 当前研究阶段在这里收尾。留下的不是一套等待补齐的统一架构，而是一组能够运行的工程零件、能重放关键反例的实验，以及一条保留自我修正过程的知识链。

这次收尾是一项研究与工程取向的决定：不再为了产出独立 JS/TS 元系统或 Locus Core，继续为它寻找必须存在的理由；后续更倾向于在具体工作和 Agent Harness 实践中使用已有系统，让新的需求和能力接受持续检验。它不是某个实验推出的“不可能性定理”，也不意味着已有工作只是一次失败的尝试。

本文依据[案例1](cases/1-heterogeneous-engineering-workspace.md)、[结论1–11](conclusions/)、研究记录、公开代码和提交历史，综合解释这段过程。**实测**指仓库受控实验或明确记录的现场观察；**文献事实**沿链接追溯一手来源；对取舍的解释属于**设计判断**，未来收益属于**待验证假设**。本文不新增实验或事实型结论，不把本次收尾决定倒写为最初就已确定的路线。运行方法与包接口集中在[README](../README.md)。

## 为什么会自然地想到对象、引用和共同工作空间

起点并不是“还缺一个框架”，而是一类很具体的接洽困难。一个工程现场同时存在机器、连接方式、GIS 服务、构建脚本、配置、制品、项目知识和能够操作它们的 Agent。它们并不缺少各自的工具，却常常缺少完成当前任务所需的联系：某个 URL 属于哪次部署，某条经验适用于哪个配置模型，机器可达是否意味着服务可用，修改文件后哪个进程才真正采用了新值。

[案例1](cases/1-heterogeneous-engineering-workspace.md)把这些问题放进持续演化的工程工作空间，而不是要求先建齐一套资源模型。这里的“共在”从一开始就包含一个约束：整合不能以抹掉原有语义、接口、身份和生命周期为代价。“流畅”则提出另一面要求：保留差异不应让每次工作都重新经历手工找人、找文档、转参数和解释上下文。

对象、引用和图因此很有吸引力。对象能将状态与操作放在相邻位置；引用能直接指向所需事物；图能表达跨资产的关系。JS/TS 又同时拥有数据构造、函数、闭包、模块和执行能力，使一种设想显得自然：如果描述工作空间的结构本身就是可执行的语言结构，是否能减少独立配置、领域模型和执行层之间的反复翻译？Agent 也许可以读取这些结构，发现能力，并在现有连接上继续构造新组合。

这是值得认真研究的可能性，不只是一个等待被纠正的误会。但它容易把两件事连接得过快：**语言内的表达统一，与跨系统的语义连续，不是同一保证。** 后来的实验不是否定函数和对象能组合，而是不断发现它们没有自动承担的责任。

有一个历史边界值得说明：当前 Git 历史从核心基线实验开始；案例文档与研究规则本身也经过后续演化。因此不能把今天案例中全部开放性措辞当作最早原型已经清楚认识所有边界的证据。反过来，也不能把研究过统一机制写成项目曾承诺必须建成统一世界。最可靠的轨迹，是看每轮实际选择了什么、由什么证据修改了下一轮的问题。

早期公开案例有更具体的痕迹：提交 `6ae9615` 中的 `documents/cases/1-evolving-production-system.md` 明确以“轻量、可演化的 JS/TS 元系统”为探索对象，用多环境、机器、服务和 CI/CD 的参考规模组织迁移、部分失败、协作冲突与修正。那是候选问题环境，不是已经部署的设施清单；它也已经区分期望、观测和操作，明确不强求统一领域模型。随后 `5950aee` 转为今天的异构工程工作空间案例。变化不是突然发现外部状态存在，而是从为元系统构造问题环境，进一步转向已有工作的实际接洽，并最终允许撤回元系统本身的必要性。旧版可用 `git show 6ae9615:documents/cases/1-evolving-production-system.md` 查阅，不恢复为现行案例。

## 第一段探索：让身份、操作和经验各自成立

[实验1–3与结论1](conclusions/1-core.md)先构造了三个小机制，而没有给它们安排统一基类或实体图。

身份作用域在内存中登记对象，跨 JSON 边界使用严格的 `{ $ref }`，由显式编码／解码恢复新的对象图。它拒绝未知或重复 ID，以及函数、循环等不受支持的 JSON 投影，不假装序列化能保留外部别名。操作目录提供发现、依赖／权限／副作用声明、显式子调用和父子 trace。经验实验则让模拟连接的成功路线改变下一次选择；再次失败就撤销建议，过期或条件变化后重新探索。

这几个机制确实能运行，也揭示了很早就重要的限制：注册并不替代原生引用；权限字符串不限制真实函数行为；失败记录不是永久规则；“经验”必须在后续选择中生效，不能只靠积累记录证明价值。严格 JSON 校验甚至成了身份原型的重要实现成本——从最小接口看不出来的责任，最终仍须有人承担。

但基线也作出过超出证据的判断：“身份只在跨序列化／恢复边界时值得注册。”[结论2](conclusions/2-workspace-tasks.md)后来明确收窄它：下一条工作区任务不需要身份注册，只能证明路径和模块引用足以完成那条任务，不能排除其他身份用途。这是一个贯穿全项目的错误模式：局部成功很容易被说成机制的普遍必要条件，局部不需要也容易被说成普遍不值得。

早期经验来自模拟连接，而不是真实 SSH 或跨机器验证。它留下了有效的策略反例，却没有证明一种通用经验引擎已经成立。后续没有强迫工程任务继承这三项原型，也没有建立兼容层来维护一种并未证成的核心架构。

## 从“机制可运行”转到“工程工作得到了什么”

[实验4–6](conclusions/2-workspace-tasks.md)把重心移到真实仓库：普通对象描述任务，显式模块组合，CLI 发现和调用，读取 package.json，经 pnpm 执行已有脚本，保留子进程输出与部分失败。由此形成今天仍能使用的 `@locus/tasks`、`@locus/workspace` 和 `scripts/locus.js`。

这里出现的实现错误很具体。终端里能运行 pnpm，不代表 Node 的无 shell 子进程能直接启动同名 shim；递归复制普通对象会泄露 Date 的可变引用；手写部分 YAML 解析会把合法转义解释错；进程退出 0 可能只是展示了帮助，没有执行指定脚本。CLI 一度还把结果 JSON 编码失败算成 `blocked`，即使任务的文件副作用已经发生。修正不是把错误隐藏掉，而是承认执行与报告是两个阶段，报告失败仍须保留真实执行状态，避免诱发重复动作。

不过，[结论3](conclusions/3-operational-experiments.md)对这轮成果提出了更根本的批评：机制正确、测试通过，不等于已经降低案例1的工程接洽成本。它仍主要在一个本地仓库内工作，还不能据此回答服务现象由什么造成、哪些外部操作有影响。实现缺陷、故障注入和能够推翻工作假设的研究性反例，都值得记录，但不是同一种研究进展。

这次修正改变了研究单位：不再按“身份、操作、经验”逐项添能力，而从一件完整的工程工作进入。[结论4](conclusions/4-infrastructure-scope.md)又增加了一次必要的纠偏：真实且可访问的业务系统，不自动是符合研究范围的好载体；应先明确基础设施问题及允许副作用，公开材料必须脱敏。真实性不是选题价值的替代品。

两次审查都没有否认已经交付的包。它们改变的是成果能支持多远，以及下一步应该由什么问题驱动。

## 两条完整闭环：绿色信号、有效配置和可复用知识

### 复制了一路的版本字符串，并不是一路独立的见证

发布研究把此前抽象的“真相与契约”压缩成一个可验证的问题：CI 成功、事件提交正确、运行端标签一致、健康检查正常，是否足够证明目标运行的是该提交构建的内容？

[结论5](conclusions/5-release-lineage.md)保留了两种不同证据。脱敏的只读现场调查发现证据链缺口，但没有取得实际制品、运行 payload 和当时的完整构建见证，因此结论是 `incomplete`，不是已经证明部署错误。公开的[实验10](../tests/10-source-binding/demo.test.js)则真实创建 Git 提交 A/B：事件指向 A，固定工作树实际在 B，制品和服务仍声明 A。标签、健康乃至制品与运行字节一致，都可以成立，只有构建现场见证揭示期望源码与实际输入不符。

这一反例的力量不在于主动让某个步骤失败，而在于**原本的绿色判定在错误内容下仍然成立**。反复核对来自同一参数的字符串，可能只证明复制链没有改字。修正需要从 A 干净检出、重新构建、交付和观测，而不是改标签或重复交付错误制品。

`@locus/deployment-audit` 将这类区别沉淀成独立取证与判定函数，可通过任务目录使用，也可直接调用。它只绑定指定 payload，依赖受信见证，不认证作者，不覆盖完整构建输入，也不证明业务可用。这些限制不是文末免责，而是下一轮实验能够继续提出问题的前提。

### 内容一致、磁盘修改、进程采用和请求成功，是四个命题

[实验11–12与结论6](conclusions/6-operations-truth-loop.md)把 Git 构建、制品和配置交付、真实 HTTP 失败、诊断、干预及知识修正接成一条闭环。同一制品发布审计 `consistent`，网关健康 200，但功能请求 502；环境配置文件覆盖了基础配置。清空覆盖文件后，旧进程仍用启动时加载的值，直到重启才恢复 200。

这次没有给抽象模型再添一个“状态”字段来宣布问题已解决，而是用干预区分了交付字节、目标文件、有效运行配置和请求结果。`environment.json` 是实验中的文件覆盖层，不是对操作系统环境变量、真实服务管理器或生产配置平台的验证。单机独立进程也没有被写成跨物理机器部署。

知识随后不只出现在结论报告里。实验实际更新 Markdown 运行手册，保留原判断、修正、适用条件及证据，将其提交并克隆，再由第二个实例读取克隆后的文档选择方法。Git 换行转换曾破坏证据哈希，促使仓库明确证据字节的检出策略，而不是放宽哈希比较。第二次处理确实少了特定探索步骤，但没有测量人类或 Agent 的总时间收益。

`@locus/operational-knowledge` 是这条闭环留下的另一件零件：校验证据路径和字节，按制品、配置模型及有效期筛选记录，保留历史修正。它不推断文字为真，不执行文档中的任意命令，也不能解决并发追加或相反解释。后来正是这些限制推动了更深入的研究，而不是意味着这个有边界的工具没有价值。

## API 的自我审查：看起来更自然，不代表责任更少

完整工程路径已经存在之后，项目重新面对最初的语言设想：[实验13与消费端研究](api-expression-study.md)比较原生模块组合、函数身份上的说明、显式观测边界和动态 Proxy 投影。它们不是一套已定架构的逐层实现，而是有不同收益和代价的候选。

实验保留了一些很有解释力的行为：替换对象不会改写已经缓存的函数；动态代理只覆盖经过代理的调用，不能替换闭包里捕获的依赖；显式核对实例可以拒绝部分错误归属，但同身份仍可能发生状态变化。说明可以被枚举，也可能与新函数脱节；普通导出对象或闭包有时能表达同样能力。

最值得留下的却是[结论8对结论7的复盘](conclusions/8-api-review.md)。初次报告把 `manual-review` 标签说成“转人工审查”，实际冲突是在修复后才追加，标签没有阻止动作；把基线调用短说成维护负担最低，却没有让各方案承担等价职责；将身份检查称为“当前证据”，实现只比较了部分归属字段。同一 subject 的旧 200 仍可复用，即使新观测已经是 502。

为什么会作出这些判断？从记录看，候选机制的命名、公共脚本提供的能力和报告中希望表达的保证，越过了各消费者实际完成的行为。工作看起来完整，验收却可能继承同一个错误前提。**比较接口的调用形状，不能代替比较谁真正承担适配、知识选择、干预与失败责任。**

这次没有为了保住候选而补成一个更大的 Runtime。实验和原判断被保留，成本排名被撤回，下一问变成了：把失效或相反证据放在动作之前，是否真的改变行为？这种修正比宣布“原生最好”更难，也更有后续价值。

## 持续演化让“保留差异”变成可观察的工程问题

[实验14](workspace-evolution.md)不再只比较一个调用点，而在同一工作空间中连续改变访问入口、交付、GIS、现有设施与知识条件，最后让新 Agent 构造只读交接组合。

其中几种区别尤其重要。旧 A/A 与新 B/B 都可以在各自时间条件下正确，新期望 B 配旧运行 A 才是冲突；历史制品必须使用构建时见证，不能拿当前 HEAD 去重验过去。资源关闭后，当前 receipt 也必须反映 closed；历史 running 快照能作为过去证据，但不能继续宣称地址在线。知识要能从持久文件冷读重建语义，不能只用固定 ID 查到记录，再从内存解释它的状态和方法。

在这个受控领域内，失效、过期或冲突知识确实在写配置／重启之前阻止了动作，有效记录才引导受限操作并重新验收。这个观察补上了实验13没有证明的行为，不意味着旧实验被追认正确，也不意味着门禁已经具备认证、事务或端到端撤销能力。[结论9](conclusions/9-workspace-evolution.md)保留了对应失败和限制。

另一个正面结果来自[新上下文 Agent 的发现过程](evidence/9-workspace-evolution/agent-discovery.md)：它从公开交接入口、源码、现有函数及协议响应中发现可用设施，复用客户端，生成网关与多个图层的真实 PNG 证据；当发布期望错误时，总体 not-ready，但 GIS 证据没有丢失。这是原生模块和领域协议形成新组合的具体例子，不是 Locus 自建发现机制成功的证据，更不是任意 Agent 可靠性的统计结论。

WMS 是本机有界协议替身，不是完整 GIS 产品。新增组合也付出了相当的验证与报告成本。[成本审查](evidence/9-workspace-evolution/cost-review.md)因此同时记录客户端复用与入口、期望版本、证据适用性、生命周期等新责任。消费者零修改不等于系统零成本；没有通用 Core 必要性证据，也不等于通用机制已被排除。

## 历史比较改变了候选方案，而不只是给已有路线增加注释

后期研究的重要变化，是不再只问“给 JS 对象补什么”，而允许不同计算与组织方式改变问题本身。[范式研究](paradigm-study.md)提出原生联邦、因果协作、查询／变化驱动和外部执行引擎四条实质不同的路线；不是同一个注册表的四种包装。

这也不是严格沿着上一轮计划走下去：结论9原本建议在第二个独立操作领域检验知识门禁；后续研究选择先考察并发历史与外部副作用，而没有完成那个跨领域对照。它拓宽了竞争解释，却没有因此补齐领域复用和长期成本的证据缺口。

### 已有系统承担的不是一种共同的“历史”

[因果历史专题](causal-history-study.md)通过实际 Automerge 3.5.0 实验，把并发修订从“保存最后一份 JSON”变成可检查的因果分歧。合并正反顺序收敛，冲突与 Counter 可保留，二进制保存／恢复维持这些语义；JSON 投影再导入却丢失了它们。这进一步限定了早期“JSON 无损”的说法：对某份显式数据契约无损，不等于对原系统的历史和类型保证无损。

但成熟 CRDT 也不能自动成为知识权威。[实验15](../tests/15-causal-history/demo.test.js)中逐字段合并形成了没有作者单独提交过的拼合记录；不同字段的修改还能使时间区间非法，却没有同键冲突。actor ID 可以自报，不能当作者认证；局部没有已知缺失依赖，也发现不了尚未收到的离线反驳。

这些不是 CRDT 不可用的证明。专题保留了不可变完整 proposal、版本指针与领域 CRDT 等强反方，尚未实现，不能宣布其成本赢家。Git 的提交树、因果变更、事件溯源和执行历史也不该被压成一个“history”字段：它们保存的单位、合并责任和重放效果不同。

### 派生关系减少一种同步债务，却不会摄取世界

[实验16](../tests/16-derived-decisions/demo.test.js)实际使用 Vue reactivity 和 Node SQLite。原生函数每次重算与响应式派生，都能在追加反证后撤回判断；SQL 可以直接从事实推导“有支持且没有反证的方法”，不必手工维护每条派生边。普通函数是有效的强基线，响应式不是正确性的必选升级。

但第二个数据库连接更新后，直接查询已变化，`computed(SQL查询)` 仍缓存旧值，直到显式摄取信号使其失效。本地 `BEGIN IMMEDIATE` 能串行化接纳意图；反证后来抵达，新的意图被拒绝，旧意图却仍实际写出了文件。实验刻意没有靠再加一次重查遮住边界。

[结论10](conclusions/10-semantic-boundaries.md)由此把探索、派生判断和动作承诺区分开。这个区分也必须保留反方：若接纳本来授予不可撤销的有界权利，旧意图完成可以符合契约；若要求新反证撤销所有未执行动作，执行器就必须参与。不能从一个非单调的“无反证”查询推出所有动作都必须全球协调。CALM、I-confluence 和 escrow 是这项讨论的文献依据，不是本仓重新发明或实验性证明的定理。

### 统一环境、窄接口和强基底都留下了正面答案

[执行与互操作专题](execution-history-study.md)说明，构建、协调、持久工作流和能力运行时早已有各自的难题与机制：Nix 关心构建输入和依赖闭包；Pulumi 区分语言执行、资源期望、引擎和 provider；Temporal 通过事件历史与 Activity 边界承担受约束的控制流恢复；对象能力将可调用引用与权力联系，而不是给普通函数添一条权限说明。它们提供了应该优先研究和复用的既有解法，**不等于已经解决本项目全部跨系统问题**。本仓未运行这些引擎，也没有做等价成本试验。

[结论11](conclusions/11-coexistence-lineage.md)则把历史问题重新打开。Smalltalk／Self 与 Webstrates 展示共同活环境的直接性；Unix 和 OGC 展示不共享完整对象世界仍能沿窄接口组合；Unison 和 Denicek 提供更强代码／编辑历史基底的竞争思路。它们不是依次被淘汰的落后阶段，也不是某种架构的装饰性先驱。

尤其有价值的是既有研究自己的失败。Cambria 放弃写入时向全部已知 Schema 提前转换，因为未来 Schema、并发注册与预转换成本使这种统一难以成立，转而保存原始变更并按读取目标转换；但它仍是有未解边界的研究原型。Ink & Switch 记录的可视化混乱、外部工具链和 API 设计负担，则提醒“更易表达”必须按任务与使用者评价，不能由语言图灵完备或接口简短推出。

这些来源的阅读深度并不相同：部分核对全文或源码，部分仅使用论文摘要，原专题明确记录了限制。这里复用的是其已注明范围的文献证据，不把它们写成本仓已复现的外部能力。

## 哪些认识被保留，为什么在这里收尾

没有被撤回的是共在与流畅的目标，以及对封装、组合、可检查副作用、持续演化和 Agent 参与的重视。变化的是这些词所承担的技术含义。

共在不再暗含“先进入同一对象世界”；组合不再暗含“先登记为同一种任务”；持续演化不再暗含“一套历史统管全部变化”；Agent 的生成能力也不意味着稳定契约、认证、幂等性或人工审查已经不重要。原生函数依旧有用，但不是所有保证的自然来源；复杂基底可能值得采用，也不能只因其复杂就排除。

“流畅”尤其从一种表达直觉变成了需要观察的问题：下一次工作是否少重建了上下文，转换是否丢失意义，变化后能否局部修改，失败后是否知道已经发生什么，验证责任是减少还是换了位置。[结论11](conclusions/11-coexistence-lineage.md)称之为跨边界语义连续性与有效表达成本的候选视角；这仍不是完成了度量的新理论，也不应立即变成公共元数据结构。

在这里收尾有三条依据。第一，已经有可复用的包、完整工程闭环和持续演化实例，不需要再造一个总架构才能保留它们的价值。第二，后期产生重要能力的地方，是明确选择现有机制及其保证边界，并不都需要新的 Locus 运行时。第三，多轮审查表明，继续围绕候选 API 增加字段和报告，很容易把实现完整度当成研究理由；下一段证据更应来自持续任务、成熟系统的真实使用和等价责任比较。

这三条依据支持**停止预定的系统化推进**，不支持“独立系统永远没有必要”。当前实验仍集中于一个长期案例、单机受控设施和少量语义探针；长期成本、生产运维、多人协作和不同 Agent 的行为都缺乏系统数据。收尾不是这些问题已经封闭，而是承认它们不应靠继续扩张 Prefix 来预先回答。

## 留下什么，怎样继承

工程上可以直接研究或复用四个[工作区包](../README.md#已实现的工程成果与保证边界)：可信任务调用、真实工作区脚本适配、独立发布取证／判定、证据绑定的 Markdown 知识。它们未承诺生产成熟度；复用时先读各包限制，尤其不要把目录授权当沙箱，把审计完成当发布许可，把知识匹配当语义认证。

实验上，早期 `src/` 和实验1–3保留一种候选机制的基线；实验4–6展示真实工具接入的陷阱；实验8–12保存发布、有效配置和知识复用的可重放路径；实验13保留候选 API 及被收窄的解释；实验14展示连续变化与独立消费组合；实验15–16提供成熟库与实际副作用的语义反例。当前实验目录编号跳过7，不为叙事完整补造缺失实验。运行与导航统一见[README](../README.md#研究导航)。

知识上，应继承的不只是修正后的“正确答案”，还包括支持、限定和反驳关系：[结论1](conclusions/1-core.md)连同[2](conclusions/2-workspace-tasks.md)的身份限定，[2](conclusions/2-workspace-tasks.md)连同[3](conclusions/3-operational-experiments.md)的价值审查，[7](conclusions/7-api-expression.md)连同[8](conclusions/8-api-review.md)的撤回，[9](conclusions/9-workspace-evolution.md)连同[10](conclusions/10-semantic-boundaries.md)对单源知识和执行边界的进一步限定，以及[11](conclusions/11-coexistence-lineage.md)对各种历史路线的开放比较。只摘录最终一句“没有 Core”，会丢掉这条知识链最有价值的部分。

复现上，每份结论的 front matter 用 `commit` 标签关联当时的知识单元；同提交文档引用标签而非自引用 SHA。历史临时路径不是可移植现场，公开证据快照也不是活服务；应从入口重新生成材料。现有测试证明具体行为，不证明架构优越性或普遍成本收益。

方法上，值得带走的是：先明确任务和允许副作用，让竞争方案承担等价责任；以能区分假设的观察而非报告字段验收；保留负结果，区分实现缺陷和问题定义被推翻；允许 Agent 发现、构造和质疑，也独立检查最关键的语义交接。这些方法同样可以修正，不是新框架的规则库。

## 尚未解决的问题与下一段实践

后续 Locus Harness 是一个实践方向，不是 Prefix 已实现的继承运行时。它可以从具体任务中的工具、协议、源码和文档开始，不必先迁移所有对象，也不必把现有实验函数直接稳定成 API。以下问题值得带过去，但并不组成待补齐的 Prefix 功能清单：

- **长期成本与有效表达**：跨多个版本、不同作者和不同任务时，原生组合、专用活环境与成熟引擎分别节省了什么，又把哪些成本转给维护、验证和上下文重建？缺少的是同责、长期、人／Agent 共同参与的观察，不是更多短 API 示例。
- **可更新知识与执行承诺**：离线反证分别在接纳前、提交后和效果前到达，真实执行器能否按版本前提拒绝过期动作？与不可撤销的限额权利相比，哪个契约适合领域？实验16尚无这样的执行器；只加重查仍留最后窗口。
- **知识的完整修订与权威**：不可变 proposal 或领域 CRDT 能否比逐字段合并更好地保留一条判断的整体语义？作者认证、晋级、撤销和离线协作如何共存？实验15没有实现这些替代路线。
- **持久执行与外部效果**：真实运行 Temporal 等成熟系统，在外部效果发生但完成回报前中断，观察恢复、幂等和版本责任。不能用手写日志或 Hello 示例替代这一窗口。
- **跨格式演化与来源保留**：GIS 接口、Schema、单位或坐标系变化后，按需转换、整体迁移和协议重新发现怎样比较？Cambria 与 OGC 提供候选思路，没有给本项目现成的通用答案。
- **Agent 与封装**：何时源码和少量说明已足够，何时协议或稳定接口才值得维护？一次成功发现不能回答可靠性、权限遵守或长期维护收益，更不能让生成的适配凭空获得外部系统没有的保证。

Prefix 留下的核心认识不是“不要建系统”，而是：**不要让系统存在的愿望替代对具体能力、语义责任与实际成本的研究。** 共在与流畅可以继续是方向；实现它们的语言、模型、工具与组织方式，仍应允许被未来实践改变。
